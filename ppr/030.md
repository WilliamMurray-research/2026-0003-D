## Abstract

Static thresholding mechanisms — such as the $\ge 10^{26}$ total FLOPs cut-off established in early safety frameworks — are increasingly inadequate. They fail to account for algorithmic efficiency gains, test-time compute scaling, and the continuous forward drift of baseline model capabilities.

This paper proposes a self-updating, empirical governance framework: the Dynamic Rolling-Window Statistical Outlier Metric. By evaluating candidate systems relative to a filtered reference population of foundational models released over a trailing 6-to-12-month window, I establish a dynamic, mathematically rigorous definition of "frontier" status. The framework operates under the explicit boundary condition of a sufficiently dense market release cadence, operationalized through an Asymmetric Disjunction Gate, an Efficiency Trigger, Dynamic Held-Out Evaluation Suites, a Hysteresis-Buffered Off-Ramping Protocol, a Model Identity Continuity Rule, and an Interim Auditing Architecture.

---

## 1. Core Mathematical Mechanics & Reference Population Rules

Defining a frontier system via standard deviation ($\sigma$) requires strict operational controls to prevent statistical distortion:

1. **Log-Normal Transformation:** Compute allocations, parameter counts, and benchmark win-rates exhibit severe right-skewed distributions. All $Z$-score calculations ($Z = \frac{x - \mu}{\sigma}$) must operate in log-transformed space ($\log_{10}$) for compute or log-odds space for capability metrics.
2. **Reference Population Filtering:** To prevent baseline deflation, the evaluation pool strictly excludes derivative fine-tunes, quantizations, distilled variants, and parameter-efficient adapters (PEFT). The population is constrained strictly to distinct base architectures and primary releases deployed within the trailing 6-to-12-month window.
3. **Global Population Aggregation:** Reference populations must be aggregated across international jurisdictions to prevent regional baseline distortion and eliminate regulatory arbitrage via offshore training runs.
4. **Inference Compute Integration:** Evaluated compute must represent **Total System Compute**, incorporating both pre-training FLOPs and test-time reasoning compute (e.g., search/execution trees) over standard operational benchmark runs.
5. **Model Identity Continuity & Lineage:** Model identity persists across the classification lifecycle regardless of external rebranding, marketing designations, or wrapper modifications. A system is treated as a single continuous lineage anchored to its initial baseline training checkpoint. Model identity resets—establishing a new baseline—only when a developer submits a distinct base architecture supported by an independent training compute log.

## 2. Classification Architecture: The Asymmetric Disjunction Gate

To resolve the "efficiency blind spot"—wherein highly efficient architectures achieve state-of-the-art capabilities without triggering raw compute limits—we implement an **Asymmetric Disjunction Gate (OR Logic)** for model entry.

```
                    +------------------------------------+
                    |  Candidate Model Evaluation Pool   |
                    +-----------------+------------------+
                                      |
                                      v
                    +------------------------------------+
                    | Log Compute Z >= +3.0σ  OR         |
                    | Capability Composite Z >= +3.0σ?   |
                    +--------+------------------+--------+
                             |                  |
                    YES      |                  | NO
                             v                  v
            +--------------------------------+  +-------------------+
            | Classified: FRONTIER MODEL     |  | Standard Release /|
            +----------------+---------------+  | Non-Frontier Status|
                             |                  +-------------------+
        +--------------------+--------------------+
        |                                         |
        v                                         v
+-------------------------------+   +-------------------------------+
| Capability Z >= +3.0σ AND     |   | Compute Z >= +3.0σ AND        |
| Compute Z < +1.0σ             |   | Capability Z < +2.0σ          |
+---------------+---------------+   +---------------+---------------+
                |                                   |
                v                                   v
+-------------------------------+   +-------------------------------+
|   EFFICIENCY TRIGGER FLAG     |   |     CONTAINMENT-ONLY FLAG     |
| Enhanced Proliferation Audit  |   | Physical Safety/Leakage Audit |
+-------------------------------+   +-------------------------------+

```

### Classification & Audit Specialization

$$\text{Frontier Status} \iff \left( Z_{\text{Capability}} \ge +3.0\sigma \right) \quad \mathbf{OR} \quad \left( Z_{\text{Compute}} \ge +3.0\sigma \right)$$

* **Standard Frontier Designation:** Triggered if a model exceeds $+3.0\sigma$ on either total effective compute or composite capability.
* **The Efficiency Trigger:** If $Z_{\text{Capability}} \ge +3.0\sigma$ while $Z_{\text{Compute}} < +1.0\sigma$, the system receives an **Efficiency Classification**. Algorithmic efficiency breakthroughs lower the capital barrier to capability replication. Therefore, these models trigger specialized proliferation, open-weight security, and replication-monitoring regimes alongside core alignment audits.
* **The Containment-Only Flag (High Compute / Low Capability):** If a model achieves $Z_{\text{Compute}} \ge +3.0\sigma$ but falls below $Z_{\text{Capability}} < +2.0\sigma$, it represents an inefficient or poorly aligned mega-run. It is classified under a specialized **Containment Protocol**. Full behavioral/capability compliance audits are waived or streamlined, but physical infrastructure controls, theft/exfiltration protections, and catastrophic safety checks remain mandatory. Regulators do not evaluate how well the model reasons, but enforce strict containment to prevent physical misuse or hardware hijack.

## 3. Dynamic Evaluation, Continuous Auditing & Interim Infrastructure

### Evaluation Suites & Triggered Re-Evaluation

* **Held-Out Test Suites:** Capability $Z$-scores are calculated across four orthogonal domains (*Unsaturated Formal Reasoning*, *Long-Horizon Code Execution*, *Autonomous Agentic Planning*, and *Extended Context Synthesis*) using private, held-out evaluation suites maintained by independent auditing bodies.
* **Continuous Monitoring & Cumulative Re-Evaluation Triggers:** Initial post-training evaluation establishes provisional classification. Rather than static time windows, continuous compliance relies on structural and empirical triggers:
1. **Cumulative Drift Trigger:** Re-evaluation is automatically enforced if post-training alignment, post-release fine-tuning, or RLHF result in a cumulative weight delta $\sum \Vert{}\Delta W\Vert{} \ge 10\%$ relative to the initial classification baseline checkpoint. This eliminates incremental "salami-slicing" update strategies.
2. **Primary Emergence Trigger:** Re-evaluation fires automatically if third-party red-teaming, external evaluation, or public deployment logs demonstrate novel agentic behaviors or benchmark leaps exceeding baseline projections by $> 0.5\sigma$, regardless of weight delta size.



### Pre-Deployment Enforcement & Strict Liability

To prevent market race conditions from bypassing the 7-day held-out evaluation window, deployment prior to audit authorization triggers mandatory **Provisional Self-Classification** under the strictest applicable frontier regime ($+3.0\sigma$). Unauthorized pre-audit deployment incurs strict statutory civil liability, potential commercial freeze orders, and immediate administrative penalties if subsequent held-out audits confirm undisclosed frontier status.

### Bootstrapping Interim Auditing Infrastructure

Recognizing that fully independent, state-run auditing bodies are not universally operational, we propose a **Three-Phase Auditing Transition Protocol**:

1. **Phase 1 (Hardware Attestation Safe-Harbor):** Labs run standardized open-source evaluation harnesses locally inside Trusted Execution Environments (TEEs) utilizing cryptographic hardware attestation and signed telemetry logs. Full Zero-Knowledge (ZK) execution trace proofs represent a near-term research dependency to be integrated as cryptographic overhead scales down.
2. **Phase 2 (Federated Red-Teaming Network):** Audit execution transitions to accredited third-party academic and security consortiums operating under strict non-disclosure and data-isolation agreements.
3. **Phase 3 (Full Regulatory Institutionalization):** Centralized national AI Safety Institutes maintain air-gapped, dynamic evaluation compute clusters to perform end-to-end classification.

## 5. Temporal Decay and Symmetric Off-Ramping with Hysteresis Buffer

To ensure regulatory obligations are mathematically consistent and administrative resources remain concentrated on true upper-tail risks, off-ramping must mirror the entry gate's structural logic while incorporating an administrative hysteresis buffer.

### Symmetric Off-Ramping Rule

A model exits "Frontier" status and its associated compliance burdens sunset **only when it falls below the threshold on BOTH gates simultaneously**:

$$\text{Off-Ramp Qualification} \iff \left( Z_{\text{Capability}} < +2.0\sigma \right) \quad \mathbf{AND} \quad \left( Z_{\text{Compute}} < +2.0\sigma \right)$$

```
                            +-------------------------------+
                            | Current Frontier-Class Model  |
                            +---------------+---------------+
                                            |
                                            v
                            +-------------------------------+
                            | Is Capability Z < +2.0σ AND   |
                            | Is Compute Z < +2.0σ?         |
                            +-------+---------------+-------+
                                    |               |
                           YES      |               | NO
                                    v               v
    +----------------------------------+  +----------------------------------+
    | Status: OFF-RAMPED               |  | Status: RETAIN FRONTIER          |
    | Enhanced Obligations Expire      |  | Active Compliance Maintained     |
    +----------------------------------+  +----------------------------------+

```

### Justification of the $1.0\sigma$ Hysteresis Buffer

* **Preventing Boundary Oscillation:** Moving from entry at $+3.0\sigma$ to exit at $+2.0\sigma$ creates an intentional **$1.0\sigma$ hysteresis buffer**. This prevents models hovering around the entry boundary from repeatedly toggling into and out of regulatory oversight due to minor population variance or small benchmark noise.
* **Symmetric Integrity:** If a model enters via a capability spike ($+3.2\sigma$) despite low compute ($+0.5\sigma$), it *must not* off-ramp while its capability remains elevated ($+2.5\sigma$), even if its relative compute score decays further.
* **Administrative Sunset:** Once both $Z_{\text{Capability}}$ and $Z_{\text{Compute}}$ drop below $+2.0\sigma$, high-overhead regulatory requirements (e.g., continuous real-time monitoring, specialized export reporting) automatically expire for that model version, ensuring regulatory oversight continuously scales with the true frontier.

## 6. Limitations and Discussion

The Dynamic Rolling‑Window Statistical Outlier Metric offers a flexible alternative to static compute thresholds, yet several limitations and broader considerations shape its applicability. The framework relies on a filtered 6–12‑month reference population of distinct base models, an assumption that holds only when release cadence remains sufficiently dense. As frontier development costs rise, regulatory burdens expand, or labs consolidate around fewer high‑capability systems, the rate of new base‑model deployments may decline. A sparse reference population increases variance in $Z$-score estimates and may weaken the stability of outlier detection, potentially requiring adaptive windowing or fallback baselines.

The integrity of held‑out evaluation suites represents another structural constraint. Because capability $Z$-scores depend on private, non‑contaminated benchmarks, maintaining secrecy, freshness, and isolation is operationally demanding. As the paper notes, “Capability $Z$-scores are calculated across four orthogonal domains using private, held‑out evaluation suites,” yet long‑term preservation of dataset integrity requires institutional capacity that many jurisdictions do not currently possess. Without robust evaluation governance, the reliability of capability‑based frontier classification may degrade.

Measuring Total System Compute—including inference‑time search, execution‑tree expansion, and dynamic reasoning depth—also presents practical challenges. Labs vary widely in how they implement or expose inference‑time compute, and architectures with user‑dependent or adaptive search depth complicate standardization. Although the framework’s inclusion of inference compute is conceptually correct, consistent measurement across heterogeneous systems remains an open technical problem.

The cumulative weight‑delta trigger ($\ge 10\%$ change) is designed to detect structural model drift, but behavioral divergence does not always correlate with weight magnitude. Small‑scale fine‑tuning, RLHF, or prompt‑conditioning can produce significant shifts in capability or alignment without large parameter changes. Future work may require complementary behavioral‑drift metrics, latent‑space divergence measures, or continuous capability‑based triggers to capture these subtler forms of evolution.

Regulatory coordination also poses non‑technical limitations. The proposed three‑phase auditing transition—from hardware‑attested local evaluation to federated red‑teaming and ultimately centralized national AI safety institutes—requires political alignment, funding, and international trust. Cross‑jurisdiction aggregation of reference populations is essential for preventing regional baseline distortion, yet geopolitical differences in disclosure norms and regulatory maturity may impede consistent implementation.

Finally, the framework’s hysteresis‑buffered off‑ramp ($+3\sigma$ entry, $+2\sigma$ exit) reduces oscillation but may prolong frontier designation for models whose risk profile has materially decreased. While this buffer prevents classification flapping, it may impose extended compliance burdens on systems that no longer represent upper‑tail risk. Balancing administrative stability with timely off‑ramping remains an important design consideration.

Overall, the Dynamic Rolling‑Window Statistical Outlier Metric provides a foundation for adaptive, statistically grounded frontier classification. It addresses key shortcomings of static compute thresholds and aligns governance mechanisms with the evolving landscape of frontier AI development. Yet its effectiveness depends on robust evaluation infrastructure, consistent international coordination, and continued refinement of behavioral‑drift detection. As deployment rates fluctuate and architectures diversify, governance frameworks must remain resilient to both rapid and slow development cycles, ensuring that regulatory attention remains focused on true upper‑tail risks.

## 7. Conclusion

As artificial intelligence architectures move past pure parameter scaling toward heterogeneous mixture-of-experts designs, algorithmic efficiency breakthroughs, and dynamic inference-time reasoning, static compute limits inevitably decay into regulatory obsolescence. The dynamic statistical framework advanced in this paper bridges the gap between technical reality and policy enforcement. By combining log-transformed rolling populations, an asymmetric disjunction gate, held-out evaluation audits, model lineage tracking, and symmetric off-ramping, this model establishes an adaptive, mathematically grounded, and administratively durable architecture for global AI governance.

## Technical Annex: Implementation & Operational Specifications

### Annex A: Cumulative Weight Delta Norm Specification

To eliminate ambiguity and prevent architectural evasion (e.g., concentrated shifts in attention projection matrices disguised by frozen embedding layers), the Cumulative Weight Delta ($\Delta W_{\text{cum}}$) is formally defined using the **Relative Layer-Weighted Frobenius Norm**:

$$\text{Drift}_{\text{cum}} = \frac{\Vert{}W_{\text{current}} - W_{\text{baseline}}\Vert{}_F}{\Vert{}W_{\text{baseline}}\Vert{}_F} = \frac{\sqrt{\sum_{l=1}^{L} \Vert{}W_{\text{current}}^{(l)} - W_{\text{baseline}}^{(l)}\Vert{}_F^2}}{\sqrt{\sum_{l=1}^{L} \Vert{}W_{\text{baseline}}^{(l)}\Vert{}_F^2}} \ge 0.10$$

#### Operational Rules for Auditor Implementation

1. **Scope:** Summation runs strictly over all trainable weight tensors ($W^{(l)}$). Non-trainable buffers, positional embeddings, and structural hyper-parameters are excluded.
2. **Quantization Neutrality:** If a model undergoes post-training quantization (e.g., FP16 to INT4), the norm is computed against de-quantized floating-point representations to isolate structural parameter changes from precision formats.
3. **PEFT & Adapter Modules:** For parameter-efficient fine-tunes (e.g., LoRA), $W_{\text{current}}$ represents the explicit merged weight tensor ($W_0 + \Delta W_{\text{adapter}}$). This ensures that even small adapter insertions are measured relative to their functional impact on base weights.

### Annex B: Composite Capability Vector Aggregation & Weighting

To compute a unified $Z_{\text{Capability}}$ from the four orthogonal capability domains ($k = 1, \dots, 4$), the framework applies an **Equal-Weighted Arithmetic Mean with a Floor Constraint**:

$$Z_{\text{Capability}} = \frac{1}{4} \sum_{k=1}^{4} Z_k$$

$$\text{Subject to the Generalist Constraint: } \min_{k} (Z_k) \ge +1.0\sigma$$

```
Domain Z-Scores (Z_1, Z_2, Z_3, Z_4)
         |
         v
+-------------------------------+
| Check Generalist Constraint:  |
| Is Min(Z_k) >= +1.0σ?         |
+-------+---------------+-------+
        |               |
   YES  |               | NO (Specialized Narrow Over-Fitter)
        v               v
+-------------------------------+ +---------------------------------------+
| Z_Capability = Mean(Z_k)      | | Z_Capability = Min(Z_k)               |
| Standard Aggregate Score      | | Penalized for Imbalanced Vector Profile|
+-------------------------------+ +---------------------------------------+

```

#### Rationale & Policy Parameter Calibration

* **Equal Weighting Across Domains:** Each domain—Formal Reasoning ($Z_1$), Code Execution ($Z_2$), Agentic Planning ($Z_3$), and Context Synthesis ($Z_4$)—carries a $0.25$ weighting to avoid subjective policy bias toward any single capability.
* **The Generalist Constraint:** A model achieving $+4.5\sigma$ in formal reasoning but failing to reach $+1.0\sigma$ in agentic planning or context processing represents a narrow, domain-specialized system rather than a general-purpose frontier model. The floor penalty ensures that narrow benchmark over-performers cannot inflate their composite score above $+3.0\sigma$.
* **Policy Threshold Tuning:** The $+1.0\sigma$ floor represents an empirically adjustable policy parameter derived from the historical variance of generalist versus specialist base models. Regulators may recalibrate this floor as capability distributions evolve across specific domain verticals.

### Annex C: Pre-Deployment Evaluation Sequencing, Audit Timeline & Enforcement

To guarantee that held-out evaluations prevent benchmark-contaminated or unaligned models from entering public use without creating market friction, the regulatory pipeline enforces strict pre-deployment sequencing and liability controls:

```
[ Phase 1: Training Complete ] ──► Submit Compute Logs & Initial Model Checkpoint
                                            │
                                            v
[ Phase 2: Post-Training ]    ──► Compute Provisional Z_Compute; Lock Weights
                                            │
                                            v
[ Phase 3: Air-Gapped Audit ] ──► Independent Held-Out Evaluation Suite Run (Days 1-7)
                                            │
                                            v
[ Phase 4: Classification ]   ──► Issue Frontier Status / Efficiency / Non-Frontier
                                            │
                                            v
[ Phase 5: Authorization ]    ──► Public API Release & Dynamic Emergence Monitoring

```

#### Operational Timeline & Enforcement Rules

1. **Checkpoint Lock & Lineage Registration (Day 0):** Upon training completion, the developer submits a cryptographic hash of the model weights and training compute logs to the auditing authority to anchor model identity continuity.
2. **Held-Out Evaluation Window (Days 1–7):** The model is evaluated inside an air-gapped environment using non-public test suites to establish $Z_{\text{Capability}}$.
3. **Provisional Classification & Enforcement (Day 8):** Frontier status and specialized flags (Efficiency vs. Containment) are formally issued *prior* to public API or open-weights deployment.
4. **Pre-Audit Release Enforcement:** If a developer deploys prior to Day 8 authorization, the system is automatically designated under **Provisional Frontier Status**. Unapproved deployment incurs statutory civil liability, and if post-hoc audit reveals un-flagged $+3.0\sigma$ performance, commercial freeze orders and mandatory weight containment apply immediately.
5. **Post-Release Emergence Tracking (Continuous):** Deployment logs are monitored continuously for emergent behavior exceeding provisional scores by $> 0.5\sigma$.
